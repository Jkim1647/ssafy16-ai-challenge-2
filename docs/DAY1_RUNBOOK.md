# Day 1 (09/21) 실행 순서

아침에 한 번 읽고 그대로 따라한다. 문서를 다시 읽을 시간이 없다는 전제로 썼다 —
막히면 팀 채팅(MM)에 바로 올리고 다음 사람으로 넘어간다.

CLAUDE.md의 "Day 1 운영 원칙"과 동일한 순서를 따른다: **오전에는 아무도 학습하지
않는다.** 실제 데이터가 예상과 다르면 그 시간이 통째로 낭비된다.

## 누가 무엇을 여는가 — 의존성부터 확인

```
김진영 (CPU, 30분 목표)

        │
        │  data_meta/schema_report.md
        │  + configs/base.yaml의 data.columns 확정
        ▼
  ┌─────────────────────────┬─────────────────────────────┐
  │                         │                              │
김현호 · 박건순 (로컬 GPU)   진영(35B) · 민우(122B) · 석웅(397B) (클라우드)
  notebooks/day1_baseline_9b.ipynb    notebooks/day1_cloud_model_probe.ipynb
                                       (MODEL_KEY만 각자 바꿔서 사용)
```

**B(9B baseline)와 C(클라우드 3종)는 전부 A(스키마 확정)가 끝나야 의미 있는 결과가
나온다.** 두 노트북 모두 0절에 스키마 대기 게이트가 있어서, A가 안 끝났으면 실행해도
"김진영의 스키마 확정을 기다리는 중입니다"라고 큰 글씨로 멈춘다 — 먼저 돌렸다가
엉뚱한 결과를 디버깅하느라 시간 쓰지 않게 하기 위한 안전장치다.

## 시간대별 순서

1. **09:00 — 김진영, A 노트북 시작.** ZIP 암호는 대회 시작 시 공개되는 값을 입력.
   1절(인벤토리 대조)에서 09/17 기준과 다르면 즉시 MM에 알린다.
   ZIP 안의 주최측 베이스라인 노트북 3개는 Qwen2.5 입문용 샘플 학습 튜토리얼이므로
   스키마 단서로 쓰지 않는다 — 스키마는 2절 자동 추론으로 확정한다.
   **정확한 분석이 속도보다 우선한다.** 시간이 걸려도 4-1절(회전·색상·밝기·블러)과
   3-1절(perceptual hash)까지 끝까지 돌리고, 그동안 나머지 팀원은 라벨 검수를 진행한다.
2. **09:30 전후 — 김진영, 2절(스키마) 결과를 MM에 올린다.** 6절 출력(요약 블록 전체)을
   그대로 붙여넣는다. `configs/base.yaml`의 `data.columns`를 6절 YAML 조각으로 갱신하고
   커밋·push한다 — B/C의 스키마 게이트가 이 커밋을 보고 통과한다.
3. **A 종료 후 즉시 — 김현호·박건순, B 노트북 시작 / 진영·민우·석웅, C 노트북 시작.**
   `git pull`로 방금 갱신된 `configs/base.yaml`을 받은 뒤에 열 것.
4. **B 완료 시 — 2절(9B baseline) 결과를 MM + Notion 「11」에 올린다.** 4절 출력(마크다운
   표 행)을 그대로 붙여넣는다.
5. **C 완료 시(모델별로 각자) — 5절 표를 MM에 올린다.** 9B baseline과 같은 300문항
   subset이므로 NetGain 계산이 바로 가능하다.
6. **A 나머지 절(3~5절: 무결성/누수, 이미지 분포, 질문 유형)은 B/C가 도는 동안 이어서
   완료하고 결과를 공유한다.** B/C를 막지 않으므로 순서상 급하지 않다.
7. **Day 1 종료 시 — 후보 모델 3개로 압축**(주력 1 / 보조 1 / 다양성 1, CLAUDE.md
   "Day 1 운영 원칙" 참고). 오답 taxonomy 분석은 B/C의 predictions.jsonl로 진행한다.

## 라벨 품질 감사 — 500개, 건순·민우·현호 각 ~167개

**목적은 label noise 추정치(= 검증 Accuracy 상한)다.** 사람이 보는 것은 train·dev뿐이다 — Kaggle 기본규칙
4-b가 validation·test 레코드의 수동 라벨링을 금지하므로 `build_audit_package.py`는 test가 한 행이라도
섞이면 경고가 아니라 **에러로 멈춘다.** 자동 분류(프로그램)는 전 split에 돌려도 된다.

**표본 500개** (seed 고정 — 다시 돌려도 같은 500개):

| source | 개수 | 역할 |
|---|---|---|
| baseline300 | 300 | dev에서 9B baseline과 같은 함수·seed로 뽑은 표본. accuracy 계산 표본과 대응 |
| supplement | 소수 | baseline300 안에 10개 미만인 희소 유형 보충 (감사 전용) |
| forced | 소수 | 압축률 이상치·train/dev 중복·크기 극단 (감사 전용, `forced_reason` 표시) |
| train_random | 나머지 | 500까지 train에서 무작위로 채움 — train noise를 dev와 따로 추정 |

label noise는 **baseline300 + train_random**(무작위)으로만 계산한다. supplement·forced는 일부러 모은
편향 표본이라 노이즈 비율에 넣으면 상한이 왜곡된다. 집계 스크립트가 자동으로 분리한다.

**진행 순서**

1. (누구든 한 명, ~2분) 자동 분류: `python tools/classify_questions.py`
   UNKNOWN 비율이 30%를 넘으면 `RULES`를 보강하고 다시 돌린다.
2. (권장) 09/21 실데이터로 중복 재검증: `python tools/extract_duplicates.py`
3. (김진영, ~2분) 패키지 생성: `python tools/build_audit_package.py`
   - 실행 중 zip 암호를 입력한다. **암호는 저장소·시트에 적지 말고 MM DM으로만 공유한다.**
   - `data_meta/label_audit/`에 **작성용 엑셀 `label_audit_500.xlsx`**, 같은 내용의 `label_audit_500.csv`, 이미지 `label_audit_images_500.zip`이 나온다.
   - 사전 설치: `pip install pyzipper` (또는 `pip install -e .[audit]`)
4. (김진영) `label_audit_500.xlsx`를 **팀 구글 드라이브에 올려 구글시트로 열고 공유**한다. 드롭다운(데이터 확인란)·필터·고정 행이
   이미 걸려 있고 유지된다. 첫 시트가 '라벨링'이어야 나중에 CSV로 내려받을 때 그 시트가 나온다. 팀 계정 안에서만 공유하고 링크 공개는 켜지 않는다.
   각자 필터에서 `담당`이 자기 이름인 행만 본다.
5. (건순·민우·현호) 이미지 zip을 파일로 받아 **이 zip만** 푼다(전체 데이터 zip 불필요).
- (개별 문항 서술 생략)
6. (각자, ~1시간) `담당`이 자기 이름인 행만 채운다.
   - `유형확정`: 자동 분류(`auto_type`)가 맞으면 그대로 둔다. 틀리면 고친다.
   - `라벨정확`: 제공된 정답이 이미지·질문과 맞는가 — 맞음 / 틀림 / 애매. **이 열이 핵심이다.**
   - `판독가능`: 이미지에서 답을 읽어낼 수 있는가 — 선명 / 흐림 / 판독불가.
   - `메모`: 애매하면 이유를 한 줄. 억지로 맞추기보다 "애매"가 더 정확한 정보다.
   - 판단이 안 서면 혼자 붙잡지 말고 MM에 올린다.
7. (전원 완료 후, 김진영) 시트를 CSV로 내려받아 `data_meta/label_audit/label_audit_500_filled.csv`로 저장하고
   `python tools/merge_label_sheets.py`
   - 출력: dev·train별 noise(틀림+애매, 95% 신뢰구간), 자동 분류 정확도, 가장 많이 틀린 규칙 Top 5, 유형별 판독가능 분포.

**MM에 올릴 것: dev label noise 한 줄.** 예: "dev noise 3.2% → 검증 Accuracy 상한 약 96.8%" — 「06」 9절과
목표 Accuracy 재조정의 근거가 된다. "애매"는 사람마다 기준이 달라 구간이 넓으므로 신뢰구간과 함께 읽는다.

(이전 방식인 5인 엑셀 시트 `build_label_sheet.py`는 이 절차로 대체됐다. 표본 선정 함수를 재사용하므로 파일은 남겨둔다.)

## 하드웨어 리스크 — 로컬 5060 Ti 사용 전 반드시 확인

09/18 세션에서 로컬 PC(`<호스트명>`)가 하드웨어 레벨로 **하루에만 2번, 누적 4번**
예고 없이 꺼지거나 GPU가 응답 불가 상태(`GPU is lost`)에 빠졌다. Docker 컨테이너로
감싸도 막히지 않는다 — 물리 GPU/드라이버/전원 공급 장치를 그대로 공유하기 때문이다.
PREFLIGHT_LOCAL.md의 "크래시 원인 분석" 절에 상세 원인과 이 PC의 실사용 가능 범위가
정리돼 있다 — **로컬 GPU 작업을 시작하기 전에 그 절을 먼저 확인할 것.**

### 재부팅 후 매번 해야 하는 것

`nvidia-smi -pl 150`은 **재부팅하면 풀린다.** GPU 작업을 시작하기 전에 매번:

1. 관리자 권한 PowerShell 열기
2. `nvidia-smi -pl 150` 실행
3. `nvidia-smi --query-gpu=power.limit --format=csv`로 `150.00 W`인지 확인
4. 150W가 아니면 GPU 작업을 시작하지 말 것

### VRAM 근접 로딩도 리스크다 — 전력만 보지 말 것

크래시가 전부 **연산 중이 아니라 모델 로딩으로 VRAM이 16GB의 98% 근처까지 차오르는
순간**과 겹쳤다(한 번은 전력이 24.65W로 매우 낮았을 때도 발생). 전력 상한을 걸었다고
안심하지 말고, 로딩 단계에서 멈춘 것처럼 보여도 기다리는 것 외에 별다른 조치가 없다.

### 꺼졌을 때

1. 당황하지 말고 재부팅
2. 재부팅 후 `nvidia-smi`로 GPU가 다시 보이는지 확인
3. 위 "재부팅 후 매번 해야 하는 것"을 다시 수행
4. 실행 중이던 노트북의 `power_log_*.csv`(꺼지기 직전까지 1초 단위로 남아 있다)를
   그대로 팀에 공유 — 크래시 시점 진단에 필수 증거다
5. Docker 컨테이너가 내려가 있으면 `docker compose up -d`로 재시작
