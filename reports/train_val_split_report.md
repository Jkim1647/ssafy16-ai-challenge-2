## 왜 train에서 검증셋을 떼는가 — dev는 못 쓴다

주최측 방송: 5명 라벨러 중 **4명 이상이 합의한 문항만 train/test로 채택**되고, 합의
미달 문항이 **dev**로 간다. 따라서 dev는 "어렵거나 라벨러 의견이 갈린" 문항만 모인
**편향 표본**이라 train/test와 분포가 다르다. dev를 검증셋으로 쓰면 검증 점수가 실제
test 성능을 대표하지 못한다. → 검증셋은 **train에서** 뗀다.

## 베이스라인 valid와 다른 점

베이스라인의 valid는 학습 루프 안에서 로스 계산에 쓰여 성능이 **과대평가**된다(주최측
방송에서 직접 지적). 이 split의 `val`은 **학습에 일절 쓰지 않는 순수 holdout**이다.
학습 코드는 `split==train` 행만 학습에 쓰고 `split==val`은 오직 평가에만 쓴다.

## 이미지 중복 처리 (누수 차단) — 실측 9쌍

같은 이미지가 다른 질문으로 train에 두 번 들어간 경우, train/val로 가르면 모델이 같은
이미지를 양쪽에서 보게 되어 검증 점수가 부풀려진다(누수). 2026-09-21 train 6,714장
전수 실측으로 확정한 중복:

| 방법 | 결과 |
|---|---|
| SHA-256 완전 동일 | 7쌍 |
| 재인코딩(dHash≤2를 32×32 gray **픽셀 MAE≤4로 확정**) | 2쌍 |
| **합계 (확정)** | **9쌍 = 18장 (0.33%)** |

확정 9쌍은 전부 dHash 거리 0, 픽셀 MAE ≤ 0.11로 명백한 동일 이미지다. 9쌍 중 **7쌍은
정답이 서로 다르다**(같은 이미지 + 다른 질문) — 그래서 반드시 같은 폴드에 묶어야 한다.

> **정정:** 사전 분석에서 "11쌍(재인코딩 4쌍)"으로 집계됐으나, dHash≤2 후보를 픽셀
> 디코딩(32×32 gray MAE)으로 재확정하니 **실제는 9쌍**이다. 나머지 후보(dHash 4~8,
> 51쌍)는 MAE 8~33으로 서로 다른 장면이다 — dHash 사슬 연결이 만든 오탐이다.

중복 9쌍은 전부 **train**에 둔다(같은 폴드 → 누수 0). 자기검증: 중복쌍이 train/val로
갈린 건수 = **0**.

## 분할 파라미터와 결과

- `seed = 1` (base.yaml과 동일), `val_fraction = 0.10`, id 정렬 후 정답별 층화 추출 → **결정론적·재현 가능**
- 중복 18장은 train 고정, 나머지 6,696 단독 이미지를 정답(a/b/c/d)별 10% 추출

| split | 행 수 | 비율 | a | b | c | d |
|---|---|---|---|---|---|---|
| train | 6,045 | 90.0% | 0.253 | 0.245 | 0.256 | 0.246 |
| val | 669 | 9.96% | 0.253 | 0.245 | 0.256 | 0.247 |

정답 분포가 train/val에서 소수점 셋째 자리까지 일치한다.

## 사용법

```python
import pandas as pd
split = pd.read_csv("data_meta/train_val_split.csv", encoding="utf-8-sig")
train_ids = set(split.loc[split.split == "train", "id"])
val_ids   = set(split.loc[split.split == "val",   "id"])
# train.csv를 id로 join해서 각자 학습/검증에 쓴다. val은 학습에 절대 넣지 않는다.
```

**팀 전원이 이 CSV를 그대로 쓴다.** 각자 다른 분할을 쓰면 오늘 나오는 실험 결과를 서로
비교할 수 없다. `tools/make_train_val_split.py`로 언제든 동일하게 재생성된다.
